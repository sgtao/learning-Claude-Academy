badge: まず定義
## プロジェクトは、==専用の作業場==
lead: 原本の定義：独自のチャット履歴・ナレッジベース・指示を持つ自己完結型の環境
- **ナレッジ**：アップロードした資料が、そのプロジェクト内のすべてのチャットで使われる
- **指示**：トーン・専門性・回答スタイルなどを書き、全チャットに適用される
- **チャット履歴**：プロジェクトごとに独自の履歴を持つ
- **効果**：毎回同じファイルを再アップロードする必要がなくなる
point: 資料と決まりごとを「置いておく」ことで、伝え直しが減る
note: 根拠：原本（見出しなし）の冒頭の定義と、要点のまとめ。解説メモ 02 の「3. セクション別の解説」。
note: 補足を足した箇所：なし（「伝え直しが減る」は原本の「毎回同じファイルを再アップロードする必要はもうありません」に基づく言い換え）。

badge: Why So
## いつ使い、どう育てるか
lead: 一度きりの質問ではなく、継続的な作業に向く
- **向く条件 1**：繰り返し使う参考資料がある（会議メモ・レポートなど）
- **向く条件 2**：回答方法に一貫した要件がある
- **向く条件 3**：チームで同じ基盤から作業する
- **焦点を絞る**：特定のユースケースから始め、あとで足す
- **最新に保つ**：古い資料は古い回答につながる
- **明確に書く**：曖昧な指示は一貫性のない結果につながる
- **名前を付ける**：資料にわかりやすい名前を付け、質問で名前を出す
point: 小さく始めて、資料と指示を更新しながら育てる
note: 根拠：原本（見出しなし）の「継続的な作業」の説明と、「プロジェクトを最大限に活用するために」の 5 項目。解説メモ 02「4. ユースケース」、05 相当の「詳細解説」。
note: 補足を足した箇所：「小さく始めて育てる」は 5 項目の整理（解説メモの活用案・案2 の表現）。原本に無い数値・事例は足していない。

## 作成は==6 ステップ==
lead: 原本の順序のまま。所要は原本に「数分」とだけ書かれている
```steps
style: cards
items:
  - icon: "1"
    title: プロジェクトページへ
    desc: 左サイドバーの「プロジェクト」をクリック
  - icon: "2"
    title: 新規プロジェクト
    desc: 右上の「+ 新規プロジェクト」をクリック
  - icon: "3"
    title: 名前を付ける
    desc: わかりやすい名前にする
  - icon: "4"
    title: 説明を追加
    desc: Claude は説明を直接見ない
  - icon: "5"
    title: 公開設定
    desc: 非公開、または組織と共有
  - icon: "6"
    title: 指示とファイル
    desc: 指示を書いて保存し、「+」でファイルを追加
    tone: outline
```
point: 設定が終われば、プロジェクト内でチャットを始められる
note: 根拠：原本（見出しなし）の 5 項目の手順（1〜5）と、そのあとの「Instructions」「ファイルメニュー」の説明（6）。解説メモ 05 相当の「詳細解説」の表。
note: 「共有の公開設定」は Claude for Work ユーザー向けと原本に書かれている。補足を足した箇所：なし。原本は作成を 2 回説明しており（3 つのステップ版と 5 項目版）、ここでは 5 項目版を使った。

## 指示に書く==4 つの内容==
lead: 「Instructions」で指示パネルを開く。全チャットに適用される
| 内容 | 原本の例 |
|---|---|
| コンテキスト | このプロジェクトは、B2Bソフトウェア製品のマーケティングコンテンツを作成するためのものです。 |
| プロセス | まず、このオーディエンスを引き付けるブログ構成を検討し、次に下書きを作成してください。 |
| トーンとスタイル | プロフェッショナルでありながら会話的なトーンを使用してください。 |
| 具体的な要件 | マーケティングコピーの最後には必ずコールトゥアクションを含めてください。 |
point: 指示は、このプロジェクト用に Claude の動作をプログラミングするもの
note: 根拠：原本（見出しなし）の「効果的なプロジェクト指示には通常、以下が含まれます」の 4 項目と例文（例文は原本のまま、一部を抜粋）。解説メモ 05 相当の「詳細解説」の「2. 指示を書く」。

## 資料が増えると、==RAG に自動で切り替わる==
lead: 利用者の操作は変わらない（視覚的なインジケーターが出る）
```diagram
type: flow
nodes: ["資料を追加", "上限に近づく", "RAG に切替", "関連部分を取得", "回答"]
labels: ["PDF・DOCX など", "コンテキストウィンドウ", "検索拡張生成", "質問に関連する情報のみ", "容量は最大10倍に拡張"]
```
point: 会話中だけのアップロードは、ナレッジとは別に保持される
note: 根拠：原本（見出しなし）の「プロジェクトナレッジがコンテキストウィンドウの上限に近づくと…」の段落と、「プロジェクトのナレッジベースに追加せずにコンテンツを使用したい場合も…」の段落。解説メモ 03 の回答 1・2。
note: 補足を足した箇所：なし。「最大10倍」が何を基準にした倍率かは原本に書かれていない（スライド 8 に要確認として載せた）。

## 共有の==3 つの権限==
lead: 共有は Claude for Work（TeamおよびEnterprise）のユーザー向けとして書かれている
| 権限 | できること |
|---|---|
| 閲覧可能 | 内容を見る・ナレッジを使う・チャットする（変更はできない） |
| 編集可能 | 指示の変更・ナレッジの更新・メンバー管理など |
| オーナー | プロジェクト作成者。誰が見られるかも含めてすべてを管理 |
point: 権限を使い分けると、安全性を保ちながら共同作業できる
note: 根拠：原本（見出しなし）の「プロジェクトを共有する際、3つの権限レベルから選択できます」の項目と、「プロジェクトで誰が何をできるかを制御する3つの権限レベルがあります」の段落。解説メモ 03 の回答 4。
note: 補足を足した箇所：なし。無料・個人向けプランでの共有の可否は原本に書かれていない（スライド 8 に要確認として載せた）。

## まとめ：持ち帰る教訓と次の 1 つ
1. **なぜ**：繰り返す仕事は、資料と決まりごとを置いておくと、伝え直しが減る
2. **どう分ける**：資料はナレッジ、決まりは指示、その場かぎりは会話中のアップロード
3. **次に試す 1 つ**：継続的な作業を 1 件選び、名前・指示・資料を決めてプロジェクトにする
> 自分への問い（原本）：継続的な作業は何か／再アップロードや再説明をしそうな資料は何か／共有したいナレッジと指示はあるか
note: 根拠：原本（見出しなし）の「次に進む前に、考えてみてください」の 3 つの問い（引用の下の行）と、要点のまとめ。解説メモの README「生成AIの総括」。
note: 補足を足した箇所：教訓 1・2 の整理は解説メモの総括（作成者の整理）で、原本の文ではない。「次に試す 1 つ」の具体化も解説メモ 02「4. ユースケース」の【補足】に基づく。
