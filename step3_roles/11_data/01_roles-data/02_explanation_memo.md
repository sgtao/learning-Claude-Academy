## 解説
### 1. 要約
このページは、Claude Academy の「データ」の役割ページです。内容は二つに分かれます。一つは「プロンプトを試す」で、SQL の作成、データパイプラインのデバッグ、A/B テストのレポート、ダッシュボード、週次の指標レポート、データファイルのクレンジングといった依頼文が並びます。どれも下書きとして開かれ、送信前に編集できます。もう一つは「使用事例」で、実際のワークフローをステップごとに説明する、ユースケース（10分）とチュートリアル（13分）が載っています。ページ自体は一覧であり、各事例の手順や結果は本文に書かれていません。

### 2. 例え話
【補足】このページは、料理教室の入口に貼られた「今日のメニュー表」と「レシピ集の目次」に似ています。メニュー表（プロンプト）は、選べば下ごしらえ済みの材料が手元に届き、味付けは自分で直せます。レシピ集の目次（使用事例）は、実際の調理を最初から最後まで追える二冊を案内しています。ただし、目次を眺めただけでは料理は完成しません。

### 5. 理解を深める質問
#### 質問1：自分の仕事の中で、一覧にある六つの依頼のうち、いちばん近い場面はどれですか。その場面で、いま手作業でやっていることは何ですか。
- **要点**：一覧のうち自分の場面に近い依頼を選ぶ見方
- 回答：まず自分の週の仕事を思い出し、「問いに答える」「不具合を調べる」「報告をまとめる」「データを整える」のどれに時間を使っているかで、一覧の近い項目を選びます。
- 解説：一覧は、クエリ作成、データパイプラインのデバッグ、A/B テストのレポート、ダッシュボード、週次の指標レポート、データファイルのクレンジングです。本文（見出しなし）「A/B テストのレポートを作成: 結果と推奨事項を含む A/B テストのサマリーを作成します。」のように、各項目は目的が一文で書かれています。【補足】非エンジニアなら、週次の指標レポートやデータファイルのクレンジングが近いことが多いと考えられます。

#### 質問2：下書きとして開かれたプロンプトを、自分の状況に合わせて編集するとしたら、どの部分を書き換えますか。
- **要点**：下書きを自分用に編集する部分
- 回答：本文は編集する場所を指定していません。【補足】一般には、対象のデータ名、期間、読み手、出力の形といった自分の状況に関わる部分を書き換えます。
- 解説：本文には「各プロンプトは下書きとして開かれ、送信前に編集できます。」とあります。つまり、そのまま送らず、状況に合わせて直す前提です。具体的にどの語を直すかは本文に書かれていないため、実際に開いて確かめる必要があります【推測】。

#### 質問3：「データファイルのクレンジング」では、加えたすべての変更をログに記録するとあります。なぜ変更の記録が大事なのでしょうか。
- **要点**：変更をログに記録することの意味
- 回答：本文は理由を書いていません。【補足】あとから「何を、どう直したか」を追えるようにするためだと考えられます。
- 解説：本文の該当項目は「データファイルのクレンジング」で、「加えたすべての変更をログに記録します」とあります。【補足】データを整える作業は、元の数字が変わることがあります。記録があれば、結果がおかしいときに戻って確かめられ、他の人にも説明できます。

#### 質問4：ユースケース（10分）とチュートリアル（13分）は、どちらを先に読むのがよいでしょうか。その理由は何ですか。
- **要点**：ユースケースとチュートリアルの読む順番
- 回答：本文からは順番を決められません。【推測】短いユースケース（10分）から読み、必要を感じたらチュートリアル（13分）に進むのが負担の少ない順です。
- 解説：本文は「10分 ユースケース Answer the ad-hoc data question」と「13分 チュートリアル Using Databricks for Data Analysis」の二つを挙げるだけで、優先順位や前提は書いていません。【補足】チュートリアルの題名に Databricks とあるので、そのツールを使わない人は、自分の環境と合うかを先に確かめるとよいでしょう【推測】。

#### 質問5：本文に書かれていないこと（事例の中身、必要な準備、結果の品質）を、学ぶ前にどう確かめますか。
- **要点**：本文に書かれていないことの確かめ方
- 回答：使用事例を実際に開いて読み、必要な準備と結果の見方を、自分の仕事に当てはめて確かめます。
- 解説：本文に書かれていないのは、各事例の手順、必要な準備、結果の品質です。このページは一覧にとどまります。【補足】学ぶ前に、読む価値があるかを事例の冒頭で判断し、試したら自分の言葉で結果を書き留めると、振り返りに使えます。

## テーマ：データの役割ページの全体像
### 背景
データの役割ページは、プロンプトの一覧と使用事例の一覧からなる入口のページです。根拠：本文（見出しなし）「各プロンプトは下書きとして開かれ、送信前に編集できます。」

### キー概念
- 下書きとして開かれるプロンプト：送信前に編集できる（本文（見出しなし）「各プロンプトは下書きとして開かれ、送信前に編集できます。」）
- データ作業の依頼の型：クエリ、デバッグ、レポート、ダッシュボード、指標、クレンジング
- 使用事例：実際のワークフローをステップごとに説明するもの（ユースケースとチュートリアル）

### 詳細解説
| プロンプト | 本文の説明 | 【補足】非エンジニア向けの見方 |
|---|---|---|
| クエリを作成 | データに関する重要な問いに答える SQL を作成する | 自分で SQL を書けなくても、問いを言葉で渡す入口になる |
| データパイプラインをデバッグ | 失敗や遅延が発生しているパイプラインについて、考えられる原因を特定する | 技術担当者向けの色が強い。状況を伝える練習になる |
| A/B テストのレポートを作成 | 結果と推奨事項を含むサマリーを作成する | 施策の効果を報告する場面に近い |
| ダッシュボードを作成 | エクスポートしたデータから、実際に使えるダッシュボードを作成する | 手元の表を見やすい画面にまとめたいとき |
| 週次の指標レポートを作成する | エクスポートしたデータや接続済みのソースから、週次の指標をまとめる | 定例の報告を軽くする場面 |
| データファイルのクレンジング | 既存のデータファイルをクリーニングし、加えたすべての変更をログに記録する | 表記ゆれや欠けを整える作業 |

- 使用事例は二つ。ユースケースの Answer the ad-hoc data question（10分）と、チュートリアルの Using Databricks for Data Analysis（13分）。
- 根拠：本文（見出しなし）「ダッシュボードを作成: エクスポートしたデータから、実際に使えるダッシュボードを作成します。」
- 根拠：本文（見出しなし）「13分 チュートリアル Using Databricks for Data Analysis」

### 注意点・限界
- 本文は一覧だけで、各使用事例の中身、必要な準備、結果の品質は書かれていない。
- 「10分」「13分」が何の所要時間かは本文に書かれていない【推測】。読む時間か、試す時間と考えられる。
- 使用事例の題名は英語で、中身が日本語かどうかは本文からは分からない【推測】。
- 「接続済みのソース」が何を指すかは本文に書かれていない。

### ポイントまとめ

## 活用案
### 案1：実務の担当者の視点
毎週同じ数字の報告に時間を取られている担当者なら、「週次の指標レポートを作成する」のプロンプトを下書きとして開き、自分の部署の項目名や読み手に合わせて直してから送ります。出力が使えたら、直した版を自分用の定型文として残し、翌週は数字だけ差し替えます。【補足】最初は手元の小さな表で試し、結果が合っているかを自分の目で確かめてから、本番の報告に使うと安心です。（179字）

### 案2：学習者の視点
Claude を仕事で使いこなしたい初学者なら、一覧を眺めて「自分の仕事に近い依頼はどれか」を一つ選び、まず使用事例のユースケース（10分）を読みます。読んだあとに、その場面を自分の仕事に置き換えて短く書き出します。【補足】チュートリアル（13分）は題名に Databricks とあるので、そのツールを使う環境かを確かめてから読むかどうか決めます。（172字）

### 案3：思考プロセスの視点
データ作業は、問いを立て、データを整え、結果を伝えるという流れで考えると整理できます。一覧の項目を、この流れのどこに当たるかで並べ替えてみます。【補足】たとえば「データファイルのクレンジング」は整える段階、「A/B テストのレポートを作成」は伝える段階です。変更をログに記録するという本文の言葉は、あとで振り返れる形で作業を残す習慣につながります。（173字）
