## 解説
### 1. 要約
この資料は、ビジネス側から届くアドホックなデータ質問に Claude で答える手順を示します。Dataプラグイン（/write-query など）があれば出発点になりますが、無くてもプロンプトは動きます。コネクタでツールとつなぎ、スキーマのエクスポートやdbtモデル、メトリクスライブラリ、データディクショナリを1つのフォルダにまとめて許可すると、Claude は実際のテーブルとメトリクス名に対して SQL を書き、結果のテーブルと回答メモをそのフォルダに書き戻します。サンプルでは質問をそのまま貼り、要因の内訳とチャート仕様まで求めます。最後に、やったことを /adhoc-answer という Skill にして保存し、スケジュール済みタスクで新しい質問の下書きを用意させ、共有して誰に聞いても同じ数値になるようにします。

### 2. 例え話
【補足】飲食店の厨房にたとえられます。お客さんの注文（質問）は、言い換えずに伝票へそのまま書き写します。食材棚（フォルダ）に実際の食材（テーブルとメトリクスの資料）が並んでいるので、料理人（Claude）は無いものを作らずに済みます。うまくいった料理はレシピカード（Skill）にして、毎時の仕込み当番（スケジュール済みタスク）に渡します。店長（あなた）はお客さんに出す前に味見をし、全員が同じレシピカードを使うので、どの店員の料理も同じ味になります。

### 4. ユースケース
- 手順を再現する場面：【補足】「なぜ数値が動いたのか」という質問が不定期に届き、そのたびに SQL を書いて答えている場面で、同じ手順を再現できます。本文のサンプルの質問は、今四半期の EMEA の粗利益率の低下です。
- 前提の環境：Claude デスクトップアプリ、Claude に使わせたいツールのコネクタ（本文には Microsoft 365 と Snowflake の接続リンクがある）、スキーマのエクスポートなどを入れたフォルダ。Dataプラグインは、あれば出発点になるが必須ではない。
- 再現の手順：
  1. 【補足】使う資料を1つのフォルダに集め、デスクトップアプリでそのフォルダへのアクセスを許可する。
  2. 【補足】届いた質問を、言い換えずにそのまま貼り、SQL の実行・要因の説明・チャート仕様を頼み、自信が持てない箇所にフラグを立てるよう添える。
  3. 【補足】結果を確認し、命名ルールや回答フォーマットの好みを伝えて、/adhoc-answer という Skill にして保存する。
  4. 【補足】スケジュール済みタスクで、新しい質問への下書きを書き出させ、送る前に自分でレビューする。
- つまずく所：
  - 管理者がプラグインを管理していて、まだ使えないことがある。本文は、その場合はそのステップを飛ばすよう案内している。
  - スケジュール済みタスクは、デスクトップアプリを開いたまま PC の電源を入れておく必要がある。
  - 【推測】フォルダに資料が足りないと、Claude が実際のテーブル名に基づいて書けなくなる。本文には、足りないときの動作は書かれていない。
  - 本文には、コネクタの接続手順の細部、実行結果の正しさを確かめる方法、権限の設定の詳細は書かれていない。

### 5. 理解を深める質問
#### 質問1：フォルダには、どんな種類のファイルを入れ、Claude はそこに何を書き戻しますか。
- **要点**：フォルダに入れる資料と、書き戻されるもの
- 回答：入れるのは、スキーマのエクスポート、dbtモデル、メトリクスライブラリ、データディクショナリなどです。Claude はそこからモデルを読み取り、SQL、結果のテーブル、回答メモをそのフォルダに書き戻します。
- 解説：資料を渡すことで、SQL は架空のものではなく、実際のテーブルとメトリクス名に対して書かれます。出力もフォルダに残るので、あとから見返したり、次の質問の参考にしたりできます【補足】。

#### 質問2：サンプルの質問文は、Claude に何を頼んでいますか。要素に分けて説明してください。
- **要点**：サンプルの質問文が頼んでいること
- 回答：大きく分けて、(a) 質問に答える SQL を書いてウェアハウスで実行すること、(b) 何が変動を引き起こしているかを説明すること、(c) 再び聞かれないよう、ダッシュボードに追加するチャート仕様を渡すこと、の要素です。
- 解説：(b) は内訳（どのセグメントか、どの変化か、どの日付か）を求める依頼で、(c) は次回は質問者が自分で更新できる成果物を求める依頼だと、本文のコツが説明しています。(a)〜(c) の区切りは、読みやすくするための整理です【補足】。

#### 質問3：「自信が持てない箇所にはフラグを立ててください」と付け加えると、何が良くなりますか。
- **要点**：フラグを頼むと確認の順番がわかる
- 回答：「自信が持てない箇所にはフラグを立ててください」と付け加えると、下書きを確認するときにまず確認すべき場所がわかります。
- 解説：下書きの全体を同じ強さで疑う必要がなくなり、確認の時間を、不確かな点に集中できます【補足】。Claude 自身の自信の表明が正しいかどうかまでは、本文には書かれていません。

#### 質問4：スケジュール済みタスクの設定は、なぜ回答の下書きを書き出すところまでにして、送る前に人が確認する形になっていますか。
- **要点**：下書きまでにして、送る前に人が見る理由
- 回答：本文の設定は、下書きの回答をファイルに書き込み、送り返す前に自分がレビューできるようにしています。
- 解説：理由は本文に明記されていません。【推測】SQL の結果や要因の説明を、人が見ないまま社内の質問者に送ると、誤りがそのまま伝わるため、送る前の確認が入っていると考えられます。メッセージを読む前に下書きが用意されることで、確認に集中できる点も、本文が述べています。

#### 質問5：自分の職場でこの手順を試すとき、最初に確かめておくべき前提は何ですか。
- **要点**：試す前に確かめる前提
- 回答：本文から読み取れる前提は、Dataプラグインが使えるか（管理者の管理下だと使えないことがある）、Claude に使わせたいツールのコネクタを追加できるか、資料をフォルダにまとめてデスクトップアプリで許可できるか、そして自動実行するなら PC を起動したまま、スリープさせない環境か、です。
- 解説：どれも、本文の手順がそのまま前提にしていることです。本文には、各前提の確認方法の詳細は書かれていません。【補足】職場のルールで外部ツールへの接続が制限されている場合は、先に管理者に確認すると安全です。

## テーマ：アドホックなデータ質問に答える手順
### 背景
ビジネス側から、数値が動いた理由を尋ねる質問が届く。その答え方を、資料の共有から Skill 化・自動化まで1本の流れで示している（本文の全体）。

### キー概念
- Dataプラグイン：/write-query などのウェアハウス・BI 関連の Skills が出発点として入っている（本文の冒頭の段落）。
- コネクタ：Claude を各ツールにつなぐ仕組み。権限とアクセスは自分が管理する（コネクタの案内の段落）。
- 作業フォルダ：スキーマのエクスポートなどをまとめ、Claude が読み書きする場所（フォルダの案内の段落）。
- プロジェクト：フォルダから作ると、命名規則と認定メトリクスのリストが引き継がれる（フォルダの案内の段落）。
- Skill（/adhoc-answer）：ここまでの作業を保存した、再利用できる手順（Skill 化の段落）。
- スケジュール済みタスク：新しい質問に Skill を自動で実行し、下書きを用意する仕組み（自動化の段落）。

### 詳細解説
| 段階 | やること | 本文にある要点 |
|---|---|---|
| 準備 | Dataプラグインの有無を確かめる | 無くてもプロンプトは動く。管理者管理で使えないときは飛ばす |
| 接続 | コネクタを追加する | Claude に使わせたいツールごとに追加。本文には Microsoft 365 と Snowflake の接続リンクがある |
| 資料 | 1つのフォルダにまとめて許可する | スキーマのエクスポート、dbtモデル、メトリクスライブラリ、データディクショナリ |
| 質問 | 質問をそのまま貼る | SQL の作成・実行、要因の説明、チャート仕様を頼む |
| 工夫 | 要因を尋ね、再利用できる成果物を求め、手本とフラグを足す | 回答が相手の言葉に沿い、確認すべき場所が分かる |
| 保存 | /adhoc-answer という Skill にする | 命名ルールや回答フォーマットの好みを伝えてから保存 |
| 自動化 | スケジュール済みタスクにする | 平日は毎時、Teams の #analytics-requests を確認し、下書きを Analytics/Inbox/ に書く |

- 【補足】業務に当てはめるときは、「質問」「資料」「型（Skill）」「自動化」の順に整えると、段階ごとに効果を確かめやすい。

### 注意点・限界
- 本文には、コネクタの接続手順の細部、権限の範囲、実行結果の正しさを確かめる方法は書かれていない。
- スケジュール済みタスクは、デスクトップアプリを開いたまま PC をスリープさせないことが必要。
- 【推測】下書きの確認を人が行う前提のため、確認の担当者や時間を先に決めておかないと、下書きが溜まる可能性がある。
- 【推測】資料フォルダの内容が古いと、回答も古い定義に基づく可能性がある。本文は、更新の運用には触れていない。

### ポイントまとめ
質問をそのまま渡し、フォルダの資料でSQLと回答を作らせ、Skillにして下書きを自動化する。

### 確認の質問
あなたの職場で、フォルダに入れられる資料（スキーマ、メトリクスの定義など）はどれですか。

## 活用案
### 案1：実務の担当者の視点
【補足】営業企画で、毎週のように「先月、この地域の売上が落ちたのはなぜか」と聞かれる場面を想像します。まず、集計表の定義書や指標の一覧を1つのフォルダにまとめ、質問を言い換えずに貼って、要因の内訳とチャート仕様を頼みます。不確かな箇所にフラグを立ててもらえば、確認は印のついた所から始められます。出てきた下書きは自分で見直してから返し、同じ質問が来たら、チャート仕様を渡して質問者自身に更新してもらいます。（203字）

### 案2：学習者の視点
【補足】データの専門家ではない人が、まず資料の読み方を学ぶ使い方です。本文のサンプルを自分の仕事の質問に置き換え、Claude が書いた SQL と回答メモを、フォルダに残った記録として読み返します。なぜその内訳で説明したのかを Claude に尋ね、分からない用語はデータディクショナリで確かめます。回答のたびに、自分の確認の勘所が少しずつ増えていくはずです。（176字）

### 案3：思考プロセスの視点
【補足】質問が届いたら、答える前に、質問の言葉を変えない、要因を尋ねる、再利用できる形を求める、の3点で整理してから頼む習慣にします。そのあと、Skill にして、同じ型で処理できる質問と、毎回考えが要る質問を分けて眺めます。型に乗る質問は自動に任せ、人は、新しい種類の質問と、下書きのレビューに時間を使う、という使い分けが見えてきます。（168字）
