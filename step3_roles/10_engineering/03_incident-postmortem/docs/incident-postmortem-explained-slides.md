# ポストモーテムを、==Cowork で下書き==する
subtitle: 記憶ではなく記録から、責めずに書く手順（初めて読む人向け）
badges: [Claude Cowork, ポストモーテム, 技術・ハウツー]
note: 元ページは Claude Academy の「エンジニアリング：ポストモーテム」。この資料は、その解説メモをもとにしています。
---
<!-- slide: points -->
## まず、==ポストモーテム==とは
lead: 障害（インシデント）のあとに書く、振り返りの文書です
- **意味【補足】**：何が起き、なぜ起き、次にどう防ぐかを書く文書。元ページに定義はなく、一般的な説明です
- **この資料でわかること**：Cowork に下書きを作らせる手順と、頼み方の6つの工夫
- **読む前の注意**：Engineering プラグインが使えない場合は、スキルを前提にした部分を飛ばしてよい（元ページの記述）
- **元ページ**：[Claude Academy の元ページ](https://academy.claude.com/ja/use-cases/incident-postmortem)
note: 非エンジニアの方は、自分の仕事の振り返り文書（納期遅れやミスの振り返りなど）に置き換えて読んでください。これは解説メモの補足であり、元ページの内容ではありません。

## 作業は、==6つのステップ==
lead: 接続 → 材料 → 依頼 → 確認 → スキル化 → 自動化
```steps
style: cards
items:
  - icon: "🔌"
    title: 接続
    desc: 3つのツールをつなぐ
  - icon: "📁"
    title: 材料
    desc: 1つのフォルダに集める
  - icon: "💬"
    title: 依頼
    desc: 5つの要素を入れて頼む
  - icon: "🔍"
    title: 確認
    desc: フラグの箇所から見直す
  - icon: "🧩"
    title: スキル化
    desc: スキルにして残す
  - icon: "⏰"
    title: 自動化
    desc: /schedule で自動作成
```
point: 最初の4つが基本。スキル化と自動化は、うまくいったあとの==仕組み化==
note: 6つの順序は解説メモの整理です。元ページは、依頼、6つの工夫、スキル化、/schedule の順に書かれています。

## 先に==接続と材料==をそろえる
lead: 依頼の前に、Cowork が読める状態を作ります
- **接続**：Customize → Connectors で Slack・PagerDuty・Datadog。権限とアクセスは自分で管理する
- **材料**：ポストモーテムのテンプレート、ランブック、ログのエクスポート、グラフのスクリーンショットなどを1つのフォルダに
- **指定**：Cowork にそのフォルダを指定。ドラフト・タイムライン・アクションアイテムのトラッカーがそこに書き戻される
- **紐づけ**：フォルダから Cowork プロジェクトを作ると、テンプレート・重大度の定義・ブレームレス言語のガイドが常に紐づく
> 各ツールが何に使われるかは、元ページに書かれていません
point: 材料を先に渡すほど、下書きは==自分たちの形==に近づく
note: point の文は解説メモの整理です。元ページの根拠は、テンプレートを読み取りドラフトなどを書き戻す、という記述です。
---
<!-- slide: points -->
badge: ステップ 3
## 依頼文に入れる==5つの要素==
lead: 元ページの例は、インシデントのチャンネル名を示して頼む形です
- **時系列の再構築**：タイムスタンプ付きで、出来事の順序を組み立てる
- **影響の要約**：顧客への影響の要約を書く
- **原因の特定**：根本原因と寄与要因を特定する
- **担当者**：すべてのアクションアイテムに担当者を付ける
- **形式とトーン**：自分たちのテンプレートで作り、ブレームレスにする
> 例のチャンネル名は #inc-2026-04-22-checkout-5xx
point: 「何を」「どの形で」「どんなトーンで」を、依頼文で先に決める
note: 5つの要素は、元ページのプロンプト例を分解したものです。

## 頼み方の==6つの工夫==
lead: 元ページが挙げる、依頼のコツです
```steps
style: cards
items:
  - icon: "🧱"
    title: 再構築する
    desc: 要約ではなく、証拠に基づく時系列にする
  - icon: "🔗"
    title: 原因を分ける
    desc: 根本原因と寄与要因で、因果の連鎖を書く
  - icon: "🗣️"
    title: トーンを明示
    desc: 言葉がシステムの挙動に留まる
  - icon: "📄"
    title: テンプレートを渡す
    desc: 自分たちの形式にそのまま収まる
  - icon: "📚"
    title: 例を追加
    desc: 構成とトーンを例に合わせてくれる
  - icon: "🚩"
    title: フラグを頼む
    desc: 最初に確認すべき箇所がわかる
```
point: 6つ目の「自信がない部分にフラグ」は、見直しの==出発点==になる
note: 6つとも元ページの太字の見出しに対応しています。説明文は短く言い換えています。

## 責めない書き方は、==システムが何をしたか==
```contrast
example:
  title: 【補足】書き換えのイメージ（元ページに例はありません）
  rows:
    - tag: 人が主語
      text: 担当者が設定を誤った
    - tag: 仕組みが主語
      text: 設定の変更が、検証されないまま反映された
verdict:
  - { label: 書く, text: システムが何をしたか }
  - { connector: 一方で }
  - { label: 書かない, text: 誰が間違えたか, tone: warn }
```
point: 元ページの指示は、==システムの挙動==だけを記述すること
note: 上の言い換え例は、考え方を伝えるために解説メモが補ったものです。元ページの文は、システムが何をしたかを記述し、誰が間違えたかは記述しない、です。

## うまくいったら、==スキル化と自動化==
lead: 1回きりで終わらせず、チームの基準にします
- **スキルにする**：これまで行ったことをスキルにするか、フィードバックで /incident-response を編集してもらう
- **自動化**：/schedule と入力するか、サイドバーの Scheduled を開く
- **自動化の例**：平日午後6時に、過去24時間で解決したインシデントをPagerDutyで確認し、ドラフトを書き込ませる
- **共有**：カスタマイズ済みのスキルを共有すれば、全オンコールエンジニアが同じ方法で書ける
> 自動化の前に確かめる項目は、元ページに明示されていません【推測】
point: ドラフトは、レビュー会議が予定される==前に==存在しているべき
note: 自動化の例は元ページの /schedule の節にあります。書き込み先は、Incidents の下のインシデントIDのフォルダの incident-response-draft.md です。

## まとめと、==次の1歩==
1. **材料が先**：接続とフォルダで、テンプレートと記録をそろえてから頼む
2. **形を指定する**：再構築、原因の分離、ブレームレス、担当者つきの項目を依頼文で決める
3. **確認して仕組みにする**：フラグ付きの箇所から見直し、スキルと /schedule で回す
> 次の1歩【補足】：自分の仕事で、記録が残る小さな出来事を1つ選び、材料を1つのフォルダに集めてみる
point: 記憶ではなく==記録==から、責めずに書く
note: 次の1歩は、自己学習用の提案です。元ページの内容ではありません。
