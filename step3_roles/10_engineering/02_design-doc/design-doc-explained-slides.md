# 設計書（RFC）の下書きを==Claude に任せる==
subtitle: 資料を集め、頼み方を決め、Skill と毎朝のタスクで自動化する流れ
badges: [技術・ハウツー, 初めて読む人向け, 自己学習・振り返り用]
note: 元ページは Claude Academy のエンジニアリング向けユースケース「設計書（RFC）」です。この解説スライドは、解説メモの内容だけで作っています。
---
<!-- slide: points -->
## まず、==設計書の下書き==を任せる話
lead: 設計ドキュメントは、Slack のスレッドやメモの一段落から始まる
- **何をするか**：Claude に、構成と調査を任せて、設計ドキュメントの初稿を作らせる
- **自分の役割**：自分にしかわからない部分を記入し、実際の判断をする
- **使うもの**：テンプレート、過去の RFC、1 ページ概要、アーキテクチャ図を入れたフォルダ
- **【補足】RFC とは**：設計の提案を文書にして、関係者に意見を求める書類。本文には説明がない
point: 構成と調査は Claude、判断は自分、という分担がこの手順の軸
note: 本文には RFC の定義や所要時間、費用、プランの記載はありません。RFC の説明は補足として足したものです。

## 手順は、==5 つの段階==
lead: 準備 → 依頼 → 保存 → 自動化 → 共有
```steps
style: cards
items:
  - title: 準備
    desc: コネクタを追加し、資料を 1 つのフォルダに集めてプロジェクトにする
  - title: 依頼
    desc: 先行事例と 2〜3 件のアプローチを求め、決まった見出しで書かせる
  - title: 保存
    desc: ここまでの内容を /rfc-draft という Skill にする
  - title: 自動化
    desc: 平日午前 9 時に、inbox の 1 ページ概要を下書きにする
  - title: 共有
    desc: Skill を共有し、どの RFC も同じ形式で届くようにする
```
point: 段階は、解説メモの整理。本文の流れを 5 つに分けたもの
note: 5 つの段階への分け方は、解説メモ側の整理です。本文に段階の名前はありません。

badge: 段階 1
## ==準備==：資料を 1 つのフォルダへ
- **出発点**：Engineering プラグインの /system-design。管理者の管理下で使えないときは、この手順を飛ばす
- **コネクタ**：Claude に使わせたいツールごとに追加する。権限とアクセスは自分で管理する
- **フォルダに入れるもの**：RFC テンプレート、1 ページ概要やメモ、関連する過去の RFC、そのサービスのアーキテクチャ図
- **許可と固定**：Claude デスクトップアプリでフォルダへのアクセスを許可し、RFCs フォルダからプロジェクトを作る
point: プロジェクトにすると、テンプレートと過去の RFC が常に紐づいた状態を保てる
note: 本文のプロンプトはプラグインがなくても機能すると書かれています。コネクタの接続リンクは 3 つ並びますが、表示は「接続」だけで、名前は本文からは分かりません。

## ==依頼==：例は、バッチからストリーミングへ
lead: 先行事例とアーキテクチャ上の制約を調べ、テンプレートに沿って書かせる
- **依頼の題材**：イベントパイプラインをバッチ処理からストリーミングへ移行する設計ドキュメント
- **求める見出し**：問題、目標と非目標、トレードオフを伴う 2〜3 件のアプローチ、推奨案、未解決の課題
- **分担の宣言**：私にしかわからない部分は私が記入する
- **【補足】用語**：バッチ処理はまとめて処理する方式、ストリーミングは届くたびに処理する方式
point: 自分の仕事では、題材とテンプレートの見出しだけを置き換えて試す
note: 依頼文は本文のものです。置き換えて使うのは、解説メモの提案です。
---
<!-- slide: table -->
## 依頼文の==6 つのコツ==
| コツ | 得られること |
|---|---|
| 先行事例を明示的に依頼する | ウィキや過去の RFC を検索し、試みられたことを引用する |
| 2〜3 件のアプローチを強制する | 売り込みではなく、本物のトレードオフ表 |
| 自分が記入する部分を伝える | Claude は構成と調査、自分は判断に時間を使う |
| 従うテンプレートを渡す | レビュアーが予想通りの構成を目にする |
| 手本となる例を追加する | 構成と文体が手本に合う |
| 不確かな点にフラグを立てさせる | レビューで最初に確認する箇所が分かる |
note: 6 つとも本文の太字の見出しに対応しています。右の列は、本文の説明を短くしたものです。

## ==保存==して、==毎朝==自動で動かす
lead: Skill にした依頼を、決まった時刻に実行させる
```steps
style: cards
items:
  - title: Skill にする
    desc: /rfc-draft という名前で保存し、保存されたかを確認する
  - title: 概要を置く
    desc: RFCs の中に inbox を作り、新しい 1 ページ概要を保存する
  - title: 平日午前 9 時
    desc: inbox を確認し、概要ごとに /rfc-draft を実行する
  - title: 下書きができる
    desc: 構造化した下書きが、RFCs 配下の番号付きフォルダに入る
```
point: 実行中は、コンピューターの電源を入れ、スリープさせず、Claude デスクトップアプリを開いておく
note: スケジュール済みタスクは、Claude に設定を頼むか、サイドバーの Scheduled から設定できます。Skill には、テンプレート、先行事例の情報源、レビュアーの定番の質問が組み込まれます。

## ==共有==の効果と、つまずきやすい所
- **共有の効果**：どのテックリードの RFC も同じ形式で届き、レビューでは体裁ではなく意思決定に時間を使える
- **つまずき 1**：管理者がプラグインを管理していて使えないときは、その手順を飛ばす
- **つまずき 2**：自動実行は、電源・スリープ・アプリの条件が欠けると、フォルダにアクセスできない
- **本文に無いこと**：所要時間、費用、プラン、/rfc-draft の中身の細かい書き方
point: 試す前に、自分の環境で条件を満たせるかを確かめる
note: スリープの条件は、本文では、タスクの実行中にコンピューター上のフォルダを使うための前提として書かれています。

- **次の 1 つ**：【補足】6 つのコツのうち、2〜3 件のアプローチと不確かな点のフラグだけを、まず試す
